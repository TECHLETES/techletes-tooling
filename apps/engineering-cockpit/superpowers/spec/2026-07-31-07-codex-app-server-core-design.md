# 07 — Codex App-Server Schema Compatibility, Threads, Turns, and Events Specification

## Purpose

Define the primary Codex integration on top of subsystem 06's process/JSON transport. This subsystem initializes `codex app-server`, validates all protocol traffic against the schema generated by the installed supported Codex version, owns thread/turn operations, and translates version-specific messages into stable cockpit domain events.

Clarification, approvals, authentication, skills, and permission profiles are completed in subsystems 08 and 09, but their protocol messages must be recognized here.

## Authoritative protocol source

The installed Codex binary is the protocol source of truth. The implementation must not maintain a speculative handwritten copy of app-server request/result/event types.

For each supported Codex version:

1. install/pin the exact binary version in the template-derived devcontainer;
2. run the official app-server schema generator;
3. commit the generated JSON Schema files and a manifest containing Codex version, generation command, generation timestamp, and SHA-256 hashes;
4. validate inbound/outbound protocol payloads against those schemas in tests and at selected runtime boundaries;
5. fail diagnostics when the installed version is outside the tested compatibility set.

Expected generation command, verified against the pinned binary:

```bash
codex app-server generate-json-schema --out backend/cockpit/codex/generated/<version>
```

If command syntax changes, the schema-update script is updated together with the compatibility manifest. Generated files are not hand-edited.

## Python boundary strategy

The official generator does not provide the cockpit's Python domain model. Therefore:

- generated JSON Schema validates app-server wire messages;
- a small version-specific decoder extracts fields after validation;
- stable cockpit dataclasses/Pydantic models represent normalized events and operations;
- no frontend code consumes raw app-server types;
- CI regenerates the schema for the pinned binary and fails on unreviewed drift.

This avoids silently trusting guessed fields while keeping the rest of the application independent of Codex protocol churn.

## Initialization handshake

On a newly opened connection:

1. send the current schema-defined `initialize` request with a stable `clientInfo` name/version and explicitly supported client capabilities;
2. validate the response;
3. send any required post-initialize notification defined by the generated schema/test client;
4. record server version/protocol metadata and capability snapshot;
5. evaluate the required-capability matrix;
6. transition the session to initialized or fail with `APP_SERVER_INCOMPATIBLE`.

`clientInfo.name` is `techletes-engineering-cockpit`. Enterprise/OpenAI account policy incompatibility must produce an actionable diagnostic rather than falling back to an unregistered client identity.

Initialization is once per process generation. It is never retried on the same connection after an ambiguous failure.

## Required capability matrix

Hard requirements for the MVP:

- initialize successfully over stdio;
- start a thread;
- resume a known thread;
- read/reconcile a thread;
- start a turn with text input and configured working directory;
- receive thread and turn lifecycle notifications;
- receive item lifecycle and message deltas;
- receive command/file-change/diff/error notifications needed for monitoring;
- interrupt an active turn;
- receive and answer server-to-client requests required by subsystem 09.

Required after subsystem 09:

- steer compatible active turns;
- request user input;
- command execution approval;
- file-change/patch approval.

Optional capabilities are recorded and exposed in diagnostics but do not block MVP startup, for example model catalog, thread listing, compaction, review-specific methods, or experimental permissions APIs.

## Thread model

One cockpit task owns one logical Codex thread. A backend restart may create a new app-server process generation that resumes the same thread.

Persist:

- external thread ID;
- creation process generation;
- current/resumed status;
- configured working directory;
- model/reasoning settings where returned;
- sandbox/approval settings fingerprint;
- instruction/skill fingerprint;
- last reconciled turn ID and update time.

### Start

Use the current schema-defined `thread/start` method. The thread working directory is the container's verified remote workspace folder. The initial thread configuration comes from repository policy and subsystem 08.

Persist the thread ID before starting a turn.

### Resume

Use `thread/resume` on a fresh initialized connection with the persisted thread ID. Validate that returned thread metadata belongs to the expected working context. Resume does not imply an old in-flight turn is controllable.

### Read/reconcile

Use `thread/read` or the current equivalent to retrieve persisted history after restart. Reconciliation maps external turns/items to existing cockpit records by exact IDs. Missing/duplicated identities are a compatibility or recovery error, not a reason to match by text.

## Turn model

A task has at most one active turn.

### Start

Use `turn/start` with:

- exact thread ID;
- version-valid input items;
- configured working directory/context;
- supported model/reasoning/sandbox/approval settings;
- task metadata only when permitted by schema.

Persist the returned turn ID and `STARTING_TURN`/`RUNNING` transition before accepting follow-up controls.

### Steering and interruption

The core adapter exposes version-tested `turn/steer` and `turn/interrupt` methods with expected thread/turn IDs. Business rules and browser endpoints are subsystem 09.

### Completion

A turn ends only on the schema-defined terminal notification/response. Normalize status, completion reason, usage metadata, final message references, and error details. Do not infer completion from a quiet process or a final-looking agent message.

## Item and event normalization

Stable cockpit event categories include:

```text
APP_SERVER_INITIALIZED
THREAD_STARTED
THREAD_RESUMED
THREAD_STATUS_CHANGED
TURN_STARTED
TURN_STATUS_CHANGED
TURN_COMPLETED
ITEM_STARTED
ITEM_COMPLETED
AGENT_MESSAGE_DELTA
AGENT_MESSAGE_COMPLETED
COMMAND_STARTED
COMMAND_OUTPUT_DELTA
COMMAND_COMPLETED
FILE_CHANGE_STARTED
FILE_CHANGE_DELTA
FILE_CHANGE_COMPLETED
DIFF_UPDATED
USAGE_UPDATED
APP_SERVER_WARNING
APP_SERVER_ERROR
UNKNOWN_APP_SERVER_NOTIFICATION
```

Each normalized event carries only relevant fields plus:

- task/session/thread/turn/item IDs;
- source method;
- event schema version;
- source payload hash;
- timestamp observed by cockpit.

High-frequency deltas may be coalesced before durable storage, but ordering and final content must remain reconstructable. Coalescing policy is subsystem 10.

## Validation and unknown messages

- Outbound requests are validated before write in tests and optionally in debug/runtime strict mode.
- Inbound results, requests, and state-changing notifications are validated before domain use.
- An unknown notification is recorded as a warning and may continue if it has no request ID and does not invalidate known state.
- An unknown incoming request blocks/marks incompatibility because the cockpit cannot safely answer it.
- A known method with schema-invalid params fails the connection.
- The raw payload is hashed and kept only in short-lived diagnostic logs after redaction.

## Compatibility manifest

A manifest per supported version records:

```json
{
  "codexVersion": "<exact>",
  "protocolSchemaSha256": "<sha>",
  "requiredMethods": ["..."],
  "optionalMethods": ["..."],
  "knownLimitations": ["..."],
  "testedDevcontainerCliRange": "<range>"
}
```

Runtime diagnostics report:

- installed version;
- matched manifest;
- schema fingerprint;
- required/optional capability results;
- whether strict validation is active.

Automatic use of an unrecognized newer version is disabled. An operator must update schemas/tests and review drift first.

## Fake app-server

A deterministic fake server implements the supported wire subset using the same generated-schema fixtures. Scenarios include:

- initialize/start thread/start turn/success;
- message and command deltas;
- file changes and diff updates;
- user input and approvals;
- steering and interruption;
- app-server error;
- malformed/unknown message;
- crash and resume/thread read;
- out-of-order non-stateful notifications where allowed.

The fake server is a process using stdin/stdout, not an in-memory shortcut, so subsystem 06 is exercised.

## Performance and storage

- Validate critical message types synchronously in the protocol consumer; expensive full-schema validation may be sampled/disabled in production only after contract coverage proves the decoder.
- Coalesce high-frequency deltas in memory on short intervals; persist terminal/final events immediately.
- Never store unlimited command output or message deltas in one database row.
- Track token/usage metadata only when provided; do not derive billing.

## Failure taxonomy

- `APP_SERVER_BINARY_MISSING`
- `APP_SERVER_SCHEMA_MISSING`
- `APP_SERVER_VERSION_UNSUPPORTED`
- `APP_SERVER_INITIALIZE_FAILED`
- `APP_SERVER_INCOMPATIBLE`

- `APP_SERVER_TURN_ID_MISMATCH`

- `APP_SERVER_TERMINAL_ERROR`

## Testing strategy

- schema generation is reproducible for the pinned binary;
- committed schemas match regeneration in CI;
- initialization success/failure and capability matrix;
- start/resume/read thread with exact ID persistence;
- start turn and normalize every required event category;
- out-of-order response handling through subsystem 06;
- schema-invalid result/request/notification;
- unknown notification versus unknown request behavior;
- delta coalescing preserves final message/output;
- terminal completion is required before state transition;
- restart with a fresh process resumes thread and reconciles known IDs;
- unsupported installed version fails before task execution.

## Acceptance criteria

- The cockpit speaks the protocol generated by the exact supported Codex version.
- A task can initialize app-server, create/resume its one thread, start a turn, and observe structured completion.
- Exact external IDs are durable and never inferred from text.
- Protocol changes fail visibly instead of corrupting task state.
- High-level cockpit code consumes normalized events, not raw version-specific JSON.
- A fake process fully exercises the same stdio transport as the real server.
